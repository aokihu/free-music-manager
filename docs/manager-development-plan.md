# FreeMusic Manager 分阶段开发计划

## 1. 开发原则

- 后台作为独立项目和独立 Git 仓库维护。
- 每个阶段只建立一个可验收的闭环，不一次性开发完整后台。
- 桌面端与移动端同步实现；移动端保证管理能力，但不提供文件上传。
- 先用本地模拟数据确认后台信息结构，再连接文件导入和持久化。
- 现阶段不为前台提供公开 API。
- 手动上传是当前内容生产方式，音频 Tag 是曲库元数据的主要来源。
- 每个阶段运行 `npm run lint`、`npm run typecheck` 和 `npm run build`。
- Git 提交和远程推送只在用户明确要求后执行。

## 2. 技术栈

- React / Next.js App Router
- TypeScript
- Shadcn UI
- Zustand
- Tailwind CSS v4

Zustand 仅在出现跨页面或跨组件的编辑状态后使用，不提前创建空 Store。

## 3. 阶段计划

### 阶段 0：独立工程基线

目标：建立可运行、可独立提交的后台项目。

任务：

- 在 `freemusic-manager` 独立目录初始化 Next.js 工程和 Git 仓库。
- 初始化 Shadcn UI，安装 Zustand。
- 增加后台项目说明、开发约束和分阶段计划。
- 保留最小的阶段提示首页，不实现业务功能。

不包含：

- 后台导航和曲库页面。
- 文件上传与 Tag 解析。
- 登录、R2、支付和前台 API。

验收：

- lint、类型检查和生产构建通过。
- 项目可独立启动，不依赖前台仓库。

当前状态：已完成。

### 阶段 1：响应式后台骨架

目标：建立后台的信息结构，不实现真实文件操作。

任务：

- 建立侧边导航、顶部操作区、概览和歌曲管理入口。
- 建立模拟歌曲列表，显示标题、Tag、发布状态和更新时间。
- 桌面端使用侧栏，移动端使用抽屉或紧凑导航。
- 只安装当前页面实际使用的 Shadcn 组件。

不包含：

- 文件上传、Tag 解析和数据保存。
- 登录与权限。

验收：

- 390px、768px 和 1440px 无横向滚动。
- 列表状态和主要操作可通过键盘识别和访问。

当前状态：已完成。桌面端提供固定侧栏和歌曲表格，移动端提供紧凑导航和歌曲卡片；概览数据与两种列表视图均来自同一份集中模拟数据。390px、768px 和 1440px 已通过真实浏览器检查，无横向滚动，导航、表格和状态标签具有明确语义。

### 阶段 2：音频导入与 Tag 预检

目标：让管理员选择音频并在保存前看到解析结果。

任务：

- 支持手动选择单个音频文件。
- 解析标题、作者、风格、BPM、封面等标准 Tag。
- 将 mood、useCases、license、priceFen 等产品字段定义为明确的扩展 Tag 规范。
- 展示文件格式、时长、大小和缺失字段。
- 解析结果只保存在当前导入草稿中。

不包含：

- 批量导入、永久保存和 R2 上传。

验收：

- 合法文件能够生成可编辑草稿。
- 不支持的格式和缺失必要 Tag 时给出明确提示。

当前状态：已完成。桌面端使用 Shadcn Dialog 提供单文件上传窗体，支持点击选择与拖放，文件通过 `music-metadata` 的浏览器 `parseBlob` 在本地解析。结果展示格式、时长、大小、码率、采样率、声道和封面，并将 TITLE、ARTIST、ALBUM、GENRE、BPM、MOOD、YEAR 和 COMMENT 映射为可编辑导入草稿；TITLE 缺失或只有空白时使用去掉扩展名的文件名作为标题，BPM 与年份包含范围校验。缺失字段、文件过大、不支持格式及解析失败均有明确状态。移动端不渲染上传入口，只保留原有管理能力。本阶段不保存文件或曲库数据，关闭 Modal 后草稿清空。

### 阶段 3：曲库清单与本地发布包

目标：在不接入前台 API 的条件下生成前台可使用的数据。

任务：

- 编辑和确认导入后的歌曲字段，将原始音频与内嵌封面保存到本地曲库。
- 通过存储适配器隔离业务与存储实现，使用环境变量选择驱动和本地目录。
- 根据音频 SHA-256 生成稳定的歌曲 ID 和曲库清单 JSON。
- 输出试听文件、封面和清单组成的本地发布包。
- 增加字段校验、重复 ID 和重复文件检查。

不包含：

- 自动修改前台仓库。
- Cloudflare R2 和在线发布。

验收：

- 单曲保存后刷新页面仍可从本地曲库读取；重复保存同一文件时更新同一记录。
- 发布包可以被手动复制到前台项目并通过构建。
- 同一输入重复生成时不会产生无意义的数据变化。

当前状态：进行中。已完成第一小步“保存到本地曲库”：Server Action 在服务端重新校验并解析音频，本地适配器使用路径约束和原子写入保存音频、封面及 `catalog/tracks.json`；页面已切换为读取真实曲库并提供空状态。默认驱动由 `MUSIC_STORAGE_DRIVER=local` 选择，本地位置由 `MUSIC_LOCAL_STORAGE_PATH` 配置。R2 适配器和本地发布包仍属于后续小步，本阶段尚未完成。

### 阶段 4：歌曲编辑与发布状态

目标：补齐日常曲库维护能力。

任务：

- 增加草稿、已发布、已下架状态。
- 支持编辑 Tag、授权、价格和试听信息。
- 支持替换音频并保留稳定歌曲 ID。
- 增加删除和覆盖前的确认提示。

### 阶段 5：批量导入与质量检查

目标：提高 AI BGM 批量入库效率。

任务：

- 支持批量选择和队列处理。
- 汇总缺失 Tag、重复内容和格式问题。
- 增加试听检查和批量发布前确认。

### 阶段 6：管理员登录与持久化

目标：从本地工具演进为可部署的私有管理后台。

任务：

- 增加管理员身份验证和最小权限模型。
- 将草稿、歌曲和操作记录写入持久化存储。
- 增加必要的操作审计。

本阶段开始才引入服务端数据库或内部管理接口。

### 阶段 7：Cloudflare R2 发布

目标：由后台安全地上传和发布试听及完整文件。

任务：

- 分离试听文件和完整质量文件。
- 保存格式、码率、时长、大小和校验值。
- 支持替换、下架和发布失败重试。
- R2 凭据只保存在服务端。

### 阶段 8：授权、定价与权益边界

目标：为未来免费和付费下载准备管理能力。

任务：

- 管理免费、需要购买、已拥有和不可用状态所需字段。
- 使用整数分保存人民币价格。
- 管理授权文本版本、AI 生成来源和商业使用条款记录。

用户、订单、支付回调和下载权益属于后续独立阶段，不与曲库后台同时开发。

## 4. 固定执行顺序

每次开始新阶段时：

1. 复核目标、输入和不包含内容。
2. 实现最小可运行改动。
3. 检查桌面端和移动端主要路径。
4. 运行 lint、类型检查和生产构建。
5. 汇报结果，等待确认后再进入下一阶段。
